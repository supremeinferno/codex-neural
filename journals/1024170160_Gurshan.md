## Week 1 — 7 Aug 2026
The project initially relied on Streamlit for the application interface and backend flow. While this allowed for rapid prototyping, it introduced several important issues from a performance and security standpoint.

### Problems identified
- The app architecture was tightly coupled to Streamlit reruns, which caused the whole application state to refresh whenever a button or action was triggered.
- The login flow stored email and password hashes in a weak format in the database, which meant the system was vulnerable to credential exposure if the database was compromised.
- There was no session persistence model beyond the browser state, so reloading the application often broke the authentication experience.
- No rate-limiting controls existed, leaving the system exposed to brute-force attempts and abuse.
- OTP validation was incomplete and not robust enough for a secure password recovery flow.

### Recommended direction
The team decided to move away from Streamlit for the production-facing architecture and adopt a FastAPI-based backend with Vercel deployment support. This would significantly improve performance, support better API handling, and provide a cleaner separation between frontend, backend, and authentication logic.

## Week 2 — 29 Aug 2026
The architecture was redesigned around FastAPI and a more modular backend, with Vercel used for deployment-oriented hosting. The new direction improved response times and gave us a better foundation for implementing security controls.

### Key observations
- The new backend architecture introduced a clearer separation of responsibilities between API, auth, and business logic.
- However, session handling was still too dependent on user-supplied data and browser-side state, which introduced a high-risk design flaw.
- It became clear that central authentication and authorization enforcement were required across the backend rather than ad hoc checks scattered through route handlers.
- Password hashing and session persistence had to become first-class requirements, not optional post-development improvements.

## Week 3 — 5 Sep 2026
This phase focused on implementing the core security controls needed to make the app more deployment-ready.

### Untracked changes implemented
- Added server-side session management with SQLite-backed session records.
- Introduced HTTP-only cookie-based session persistence.
- Added centralized auth dependencies for protected routes.
- Implemented stronger password hashing with Argon2.
- Added login throttling and request rate limiting.
- Added logout/invalidation support.
- Added event logging for login and security-related actions.
- Began replacing the previous single-admin model with a more flexible role-based authorization layer.

### Issues faced during this phase
- The existing `main.py` and `auth.py` files had grown too large, making the code harder to maintain and reason about.
- Admin authorization was initially too dependent on a hardcoded email check.
- The in-memory rate limiter was useful for basic protection but not suitable for multi-instance production deployment.
- Frontend session restoration had to be updated so the UI could reliably restore auth state from the server.

## Week 4 — 11 Sep 2026
The security work moved from basic protection into a more production-oriented model. The team focused on making authorization more structured and preparing the rate limiting layer for deployment-level usage.

### Major changes completed
- Centralized authentication checks into a reusable auth layer.
- Extended authorization from a single admin flag into role-based and permission-based access control.
- Added a permission map for `research`, `document_chat`, and `document_upload` actions.
- Added a Redis-ready rate limiter with configurable algorithms: `sliding_window`, `fixed_window`, and `token_bucket`.
- Kept a graceful memory fallback for environments where Redis is unavailable.
- Updated the admin dashboard to expose role information and recent security event details.
- Improved event logging so the system records a broader range of operational and security activities.

### Current issues and remaining concerns
- The codebase still contains large modules that could be split into smaller service files esp for main.py
- Permissions are still relatively static in code, so assigning roles and permissions from the dashboard is not yet fully implemented.
- Redis is required for true shared-rate-limiting across instances, but the current environment still depends on whether Redis is running.
- Upload handling, SSRF protections, and deeper observability still need additional hardening before this can be considered fully production-grade.
