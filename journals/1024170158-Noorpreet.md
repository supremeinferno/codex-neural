# Development Journal — CODEX Neural

## October 10, 2026 — Persistent chat history and navigation

I worked on adding persistent chat history so people could return to earlier research and PDF conversations. Before this, the history appeared in a small floating panel that covered part of the page. I changed the navigation so the menu opens a side drawer, and History leads to its own page.

I added SQLite storage for conversations and messages, connected records to the signed-in user, and added backend checks so a user can only access their own chats. The history page lets users reopen, rename, and delete saved conversations. Research and PDF chats can be saved and continued.

One challenge was making the saved history work with both types of chat. PDF chats also need to be associated with the document they use. I added checks for document ownership so one user cannot use another user’s saved PDF through the chat endpoints.

I learned that saving chat text is only part of the feature. The application also needs to identify the user, restore the right conversation, and check ownership each time saved data is requested.

## Later work — Research chat behavior and usability

I worked on making the research chat handle ordinary messages and research requests more sensibly. The intended behavior was for the system to respond directly to casual conversation, ask for clarification when needed, and use the research process for questions that call for research—without asking the user to choose a separate mode.

I also worked on handling spelling mistakes in research queries. This matters because a typo can make it harder to find relevant information even when the user’s intended topic is understandable.

Other improvements included starring chats and adding ways to export reports. These features were intended to make it easier to return to useful conversations and keep a copy of research outside the application.

## Research pipeline debugging — date not confirmed

A difficult issue appeared when a research request failed with a Groq 413 error. At first, I suspected the request needed a different output-token setting. Trying a lower `max_tokens` value did not fix the error, and the report was cut off, so I reverted that change.

The debugging notes showed that the request was already too large before the model produced its answer. A webpage scraper was passing a very large amount of page text into the pipeline; one Wikipedia page was about 147,800 characters. That explained why the request was far beyond the reported 8,000-token-per-minute limit.

I explored retrieving more relevant text instead of sending an entire page. I tried scoring text chunks by keyword relevance and filtering out boilerplate. This improved the approach, but it did not always find the most useful passages. I also tried Mistral embeddings; the similarity scores were too close to reliably separate relevant chunks from less relevant ones. This showed me that adding embeddings alone does not guarantee good retrieval. The chunks and query also need to be chosen carefully.

I improved the Writer prompt with a target length and a “Go Deeper” section. In my notes, the report still exceeded the target, and the Sources section included dates that were not supported. Those were issues to address rather than results I considered finished.

## What I learned

I learned to investigate the source of an error before changing model settings. In the 413 case, the first explanation I tried was wrong; the oversized scraped page was the real cause. I also learned to treat retrieval and report quality as things that need testing, not as solved just because a new technique has been added.

I used the Git branch and pull-request comparison to review which files would be proposed for the project. I ran the available Python syntax and frontend build checks during the related development work. These checks help catch some errors, but they do not prove that every chat flow works correctly with a live backend and model service.

## Work still needing verification

Some research-pipeline ideas in my debugging notes were experimental or still pending, including wiring the retrieval step into the full pipeline, enforcing a strict report-length limit, preventing unsupported source dates, and adding a fact-checking step. I would verify the current branch and pull-request changes before describing any of these as completed features.
